# AGENTS.md

## Scope

- This repository is in planning/scaffold phase for a reusable AI Gateway deployable on Netlify.
- Treat [PLAN.md](PLAN.md) as the product and architecture source of truth. Link to it from new docs instead of copying large sections.
- Keep v1 small, clear, deployable, and easy to reuse from personal projects.

## Target Stack

- Runtime: Node.js 20+.
- Language: TypeScript strict.
- Backend: Netlify Functions under `netlify/functions`.
- Storage: Netlify Blobs for v1 app API key records; keep Upstash Redis behind an interface for production-grade rate limits.
- Client: exportable ESM TypeScript client under `src/client`.
 - Runtime baseline: Node.js 20+ and npm 10+. Note: Netlify's build environment uses Node.js v22 and may set a specific TypeScript compiler option during CI builds. If you see compilation or runtime mismatches between local and Netlify builds, reproduce the build with Node v22 locally and align tsconfig.json / tsc options with Netlify's environment.

## Architecture Rules

- Browser apps should call the gateway directly with a gateway app API key.
- Provider secrets stay server-side in Netlify environment variables only.
- Use provider adapters behind a shared `ProviderAdapter` contract for Gemini, Groq, and future providers.
- Keep model aliases and routing centralized in the model registry. Preserve `auto:fast`, `auto:balanced`, `auto:quality`, `auto:reasoning`, `auto:vision`, and `auto:embedding`.
- Prefer streaming SSE whenever a provider supports it. Use the standard events: `meta`, `delta`, `done`, and `error`.

## Security Invariants

- Never hardcode provider tokens, admin keys, app API keys, or peppers.
- Never return provider secrets or app key hashes from public APIs.
- App API keys must be generated by the gateway, shown in plaintext only once, and stored only as hashes using `AI_GATEWAY_KEY_PEPPER`.
- `/api/health` is public. Every other public gateway API requires an app key. Key management APIs require `AI_GATEWAY_ADMIN_KEY`.
- Validate CORS origins against each app key's `allowedOrigins` before reflecting `Access-Control-Allow-Origin`.
- Do not log prompts, image base64 payloads, API keys, provider tokens, or full stack traces. Log metadata such as `requestId`, `appId`, endpoint, provider, model, duration, status, and sanitized error code.
- Sanitize errors to the planned JSON shape and keep sensitive upstream details out of responses.

## Implementation Conventions

- Add shared helpers under `netlify/functions/lib` for auth, CORS, errors, validation, config, SSE, key storage, rate limiting, and provider registry behavior.
- Validate request payloads at the function boundary before calling providers.
- Keep `MemoryRateLimitStore` for dev/test only; make production stores replaceable through interfaces.
- Implement provider fallback only before the first streamed token. After streaming starts, emit an SSE `error` event if the provider fails.
- For vision input, validate MIME type and size, allow only `image/png`, `image/jpeg`, and `image/webp`, and never log base64 data.
- Keep the TypeScript client aligned with the API contract, including request/response types, SSE parsing, `AbortSignal`, and normalized errors.

## Testing Priorities

- Cover auth success/failure, admin auth, app key creation without plaintext storage, revocation, CORS allow/deny, payload validation, rate limiting, SSE event format, mid-stream errors, provider fallback before first token, and client SSE parsing.
- Use mock/template providers for deterministic streaming and fallback tests before depending on real provider credentials.
- Do not require real provider secrets for the default test suite.

## Push policy for `main` / `master`

- Purpose: prevent automatic Netlify deploys that consume credits.

- Operational rules:
	- Commits and pushes to branches other than `main` and `master`: allowed.
	- Commits to `main` and `master`: allowed.
	- Pushes to `main` and `master`: MUST NOT be performed automatically. Any agent, script, or workflow that intends to push to `main` or `master` must request explicit human confirmation each time before performing the push (use an ask/confirmation tool and obtain approval).

- Reason: pushes to `main`/`master` trigger Netlify deploys which may consume credits; therefore pushes must only occur after human approval.

- Recommendation: for intentional deployments prefer opening a Pull Request or performing a manual push from a developer's environment after explicit confirmation.
